# 用途・設計意図・処理の仕組み

記録日：2026-10-22。対象：2026-10-21に作成した初期版。未決事項を正式採用と扱わないための説明も含みます。

## 1. 業務上の目的と作成までの経緯

現行Ph1では、顧客データ管理・メール配信の準備・顧客登録・購読同意・配信停止を一体で整えます。初期構成はGoogle Workspace、Gmail、スプレッドシート、GASを基本案としていました。メール配信側はGoogle Workspace管理者の回答待ちなので、先に顧客情報を整理できる部分を進めました。

当初の担当範囲はSansan CSV取込、原本保持、顧客ID、重複候補の人による判断、取得経路・同意・停止の区別、再取込時の停止維持、配信候補の抽出設計でした。その後、ユーザーから次を明示的に依頼され、設計だけでなくアプリ初期版を実装しました。

- Sansan形式CSVから登録する。
- 入力画面から登録・編集し、スプレッドシートと連動させる。
- 初期ブレストどおりGASアプリとし、独立型GASで作る。
- スマホ撮影の名刺画像からも登録し、同じ重複確認を行う。
- 専用GitHubへ保存し、将来、他のAIや人がチャット履歴なしで理解できる記録を残す。

Web公開サービスへ別アプリを作る構成ではなく、GASがHTML画面を返す構成を採用しています。Gmailの送信方式を決めなくても顧客管理を準備できること、Google内に保存先をまとめられること、独立したコードと接続先を切り替えられることが意図です。

## 2. 維持する既存方針と、実装上の仮置き

以下はローカルの既存決定資料に記録された方針の要約です。この要約が決定内容を変更するものではありません。

| 方針 | 意図 |
|---|---|
| 元CSVは原則全列保存し、補正前の値も残す | 海外名、カナ欠落、複数住所、表記揺れを後で確認できるようにする |
| 毎回重複確認を行い、候補を自動統合・削除しない | 同じメールを複数人が使う場合や、転職・同姓同名を誤統合しないため |
| 顧客登録・取得経路・購読同意・停止を別に記録 | 名刺を受け取ったことと、メールを希望したことを混同しないため |
| 顧客IDを最初から持つ | 氏名やメールが変わっても顧客と履歴を追えるようにする |
| 本番メール前に権限・上限・ドメイン・停止導線等を確認 | データ管理ができたことを、本番配信の承認と混同しないため |

初期版の上限、表の構成、画面の状態名、停止解除機能を持たないことは実装上の仮置きです。取得経路や同意証拠の十分性、停止範囲、再購読、担当者、保存期間は業務責任者の確認待ちです。

## 4. 保存する情報と、スプレッドシートの役割

| 管理表 | 保存するもの |
|---|---|
| 顧客一覧 | 管理番号、氏名、会社、部署、宛先、電話、取得経路、同意、停止、版番号、更新日時 |
| 重複確認 | 入ってきた値、相手の候補、理由、未判断/判断済み、判断者・日時・理由、関連先 |
| 取込履歴 | ファイル名、照合値、原本ID、列一覧、内容あり/空行/新規/確認待ち件数、担当・日時 |
| CSV原行 | 取込ID、CSVレコード番号、全列の元値。空行の位置情報は原本を参照 |
| 変更履歴 | 操作、変更前後、アカウント、日時、操作ID。名刺・CSVの接点も追跡 |
| 名刺画像 | 原画像ID、照合値、文字読取用ドキュメントID、読取結果と状態 |
| 停止台帳 | 顧客ID、照合用メール、日時、理由、担当 |
| 処理の復旧記録 | 反映予定の情報の写しと、反映済みかどうか |

現在の保存の正本は各表の管理用JSON列です。読みやすい表示列も出しますが、**表示列だけをスプレッドシートで直接編集してもアプリには反映しません**。編集はアプリから行います。双方向の直接編集対応は未実装です。

JSONは複数項目を一つの文字列として保存する形式です。復旧記録にも顧客情報の写しを持つため、同じ個人情報管理の対象です。閲覧者・保存期間・削除方法が未確定のまま大量運用を開始しないでください。

## 5. CSV取込の意図と実際の動作

1. 利用者がファイルと文字コードを選びます。画面で件数・空行・重複候補を確認します。
2. 登録時にサーバーが再読取し、最新顧客との照合をやり直します。画面の判定結果だけは信用しません。
3. 原ファイルの内容からSHA-256という照合値を計算します。同じ内容のファイルが既にあれば取込を止めます。
4. 原本のバイト列をDriveへ保存し、元の列値を管理表へ保存します。氏名やメールを推測で補いません。
5. 候補なしの行は新規顧客、重複候補やメール形式不備のある行は確認待ちにします。
6. 新規登録しても購読同意は未確認です。

対象形式は確認したSansanの60列と順番に限定しています。列の増減・順番違いは保留とし、CSVを勝手に削って合わせません。引用符、引用符内のカンマ・改行、BOMを扱います。テキストの行数とCSVレコード数は違うため、件数はCSVとして数えます。

参考CSVのローカル確認では、60列、内容あり68件、全項目空885件でした。ファイル名にある件数は根拠にしていません。個人の値は公開記録へ転記せず、原本も書き換えていません。

## 6. 重複確認と宛先の考え方

人物ID・名刺ID（同じ取得経路）、メール、氏名と会社の組合せで候補を出します。会社IDだけ、空欄のID同士、会社代表電話だけでは統合しません。メールの大小文字差は保守的に候補扱いとし、送信先の文字を自動変更しません。

CSV全体を見てから判定するため、同じCSVの後ろにしか現れない重複も検出します。二つの行が候補なら両方を確認待ちにできます。片方を新規確認した後、もう片方を既存顧客へ関連付けられます。

- 同じ人：取得情報を履歴で関連付けます。既存プロフィール、同意、停止は上書きしません。
- 別人：理由付きで新規顧客を作ります。共有メールは別人でも宛先として確認待ちが続きます。
- 判断前：候補を残します。新規顧客として自動統合・削除しません。

初期版の確認画面には、入ってきた候補自体を訂正するフォームや、既存顧客同士を統合・分割する機能はありません。形式不備の修正や誤判断の訂正が必要な場合の操作は、追加実装前に設計してください。過去の原本を修正・削除して帳尻を合わせないでください。

## 7. 同意・停止と将来の配信側への接続

同意状態は未確認／確認手続中／同意済み／拒否です。同意済みにはメール、日時、方法、証拠参照を必要とします。本人確認や証拠の十分性を自動で保証するものではありません。

停止は顧客IDとメールで照合します。同じアドレスが別顧客IDで再登場しても停止扱いを維持します。重複確認中の登録に停止申出があれば、判断の完了を待たず停止台帳へ記録します。同意拒否も停止にします。アプリから停止解除はできません。

メールを変更した場合は、同意を未確認へ戻し、過去値は変更履歴で保持します。第2メールは保存しますが、配信用宛先の選択機能が未実装なので確認待ちです。

画面の管理状態は、停止、未解決候補や共有宛先、宛先不足、受信希望の記録不足を見ます。**将来の配信対象抽出・送信承認・送信直前の最新停止照合は、この表示だけで代用できません。** 現時点に送信処理はありません。

## 8. 名刺画像の処理

スマホで撮影または写真から選び、原画像をDriveへ保存します。Drive API v3で画像をGoogleドキュメントへ変換し、文字を読み取ります。メール・電話だけを入力候補として抽出し、氏名・会社・部署は人が画像と読取結果を見て確認・入力します。

画像の文字読取をOCRと呼びます。OCR成功は登録成功ではありません。確認して保存するとCSVや手入力と同じ候補判定へ進みます。画像から同意を推測しません。読取失敗でも原画像の記録を残し、手入力を可能にしています。設定修正後の同一画像再試行では保存済み画像を再使用します。

画像はJPEG/PNG・5MBまで。HEIC、実際のスマホ写真の精度、Googleでの文字読取所要時間は未検証です。公開リポジトリへ画像を置きません。

## 9. 権限・競合・復旧

GASの呼出ごとに利用者メールとALLOWED_USERSを照合し、取得不能・未許可なら拒否します。アプリのアクセス範囲に加え、スプレッドシート・原本保管先の権限も必要です。別名メールと実アカウントを混同しません。

初期テストの実行者はアクセスしているユーザー、利用範囲は自分のみとする案です。実際のGoogle画面の選択肢を確認し、未確認のまま全員公開にしません。

同時実行をGASのロックで制御し、編集時の版番号を確認します。保存前に変更計画を復旧記録へ書き、次に表へ反映します。途中で書込が失敗した場合は、次回操作前に未反映計画を再適用します。操作IDを記録し、同じ操作の再送で二重登録しません。

Driveへの原本保存とシートへの書込は一体の処理ではありません。原本だけが保存された場合は、未関連付けのファイルが残る可能性があります。自動削除しません。これらの照合や履歴の保管方針は継続課題です。

要求権限はスプレッドシート、Drive、Googleドキュメント、利用者メール取得です。Driveの許可には削除権限も含まれますが、今回のコードに削除処理はありません。Gmail権限は要求しません。初回の権限付与はユーザーが確認・承認します。
